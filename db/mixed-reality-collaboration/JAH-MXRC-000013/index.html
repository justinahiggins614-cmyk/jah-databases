File and Model Sharing in Space

Record: JAH-MXRC-000013 · Database: Mixed Reality Collaboration Database · Edition: public · Record kind: mixed reality collaboration record

Subject: Putting files and models into the room where everyone can see them.

Status: Live, version 1.0.0, 2026-11-18. This is a specification or a Signature design-study, not a finished deployed system.

JCC code: JAHDB/mixed-reality-collaboration#JAH-MXRC-000013 · Key: k=e6bd7856

Descriptions

Sharing in space means a file is not a link in a chat; it is a thing in the room — a document on the table, a model floating where everyone can walk around it. Files are placed by the person who shares them, and the room shows who placed each one and when. A model can be opened, turned, and measured by anyone in the room, and the original file is never changed by looking at it — a copy is made for notes and marks. Large files are checked before they enter the room, because a file too big for the room will slow everyone down. When the session ends, the shared files are filed with the room's record, so the work is not lost when the room closes. The File and Model Sharing in Space stage works through 4 parts: Shared files; Model viewer; Copy for notes; Session filing. Each part is named, tested, and filed, so the work can be checked by a stranger. This record specifies the stage completely: what it is for, how it is done, how it is tested, what it costs in time and attention, and what can go wrong. The specification is written for a builder who has never done this stage before, and for a reviewer who must judge whether it was done properly. Inside the Mixed Reality Collaboration Platform, File and Model Sharing in Space sits between the stages that come before it and the stages that come after it, and it must fit both: what it receives must be in the shape it expects, and what it hands on must be in the shape the next stage expects. Nothing in this record is a claim that the system it specifies is deployed, live, or finished; it is a specification, documented from public knowledge and established practice, and the sources at the end of this record are the public pages it was checked against.

Math Proof

The mathematical reasoning is plain arithmetic on the record's own figures. The figures are: files_filed = 48; files_shared = 48; models_opened = 36; originals_changed = 0. Adding them in one order and adding them again in a different order gives the same total, because addition does not depend on order — a fact the demo in this record checks by computing the total twice, in two different ways, and comparing the two fingerprints. The fingerprint is the SHA-256 digest, a standard fingerprint of a piece of text: the same text always gives the same fingerprint, and a different text gives a different one. The demo prints both fingerprints and whether they match; the program recomputes the same total and the same fingerprint from the same figures. The arithmetic is machine-checked by the demo; the scientific claim — that the stage, followed as written, produces the checked result — is stated, not machine-checked, and is labeled as such wherever it appears.

The equation says: add all of the record's figures together to get the total, then take the SHA-256 fingerprint of that total written as text. The demo computes the total twice, in two different orders, and the two fingerprints must be identical.

Workflow

The problem: The problem File and Model Sharing in Space solves is simple to state and hard to do well: Putting files and models into the room where everyone can see them. Without this stage, the work goes wrong in a particular way. The failure shows up late, when it is expensive to fix, and it shows up as a surprise, because nothing was recorded that would have warned anyone. The stage exists to move the failure earlier, where it is cheap, and to make it visible, where it can be fixed. The problem is not that people are careless; it is that a job with many parts and many hands needs a fixed shape, or the parts drift apart. File and Model Sharing in Space is that fixed shape for this part of the work.

The worked solution: The worked solution runs in 5 steps, in order. step 1: Place shared files where all can see them; step 2: Show who placed each file and when; step 3: Let anyone open, turn, and measure models; step 4: Never change the original by looking; step 5: File shared files with the room's record. Each step has a visible result: something written, something checked, or something handed on, so the stage can be stopped and inspected at any point. The steps are done by the person or program named in the record, and each step is checked before the next begins, because a mistake carried forward is a mistake multiplied. The parts of the stage are: Shared files; Model viewer; Copy for notes; Session filing. When a step fails, the worker stops, fixes the failure, and re-runs the step; the stage never skips a failed step and hopes the next one covers it. The whole method is written so that two workers following it would produce the same result, and a reviewer following it could find where a result came from.

The answer: The answer this stage delivers is a finished piece of work that the next stage can use without asking questions: the File and Model Sharing in Space is complete, checked, and filed. The checks that prove it are: Files are things in the room, not links; Originals are never changed by looking; Shared files are filed with the record. When those checks pass, the stage is done, and the proof is the record itself — the checks, the dates, and the names. The figures that describe this stage are: files_filed = 48; files_shared = 48; models_opened = 36; originals_changed = 0. Those numbers are the record's own checkable figures, and the demo in this record recomputes them from the figures alone, so any reader can verify them without trusting the record's word. A stage whose checks pass is a stage the factory will stand behind.

When it applies: File and Model Sharing in Space applies wherever the Mixed Reality Collaboration Platform is used: whenever a new specialist, a new routing, a new room, a new building, or a new property must pass through this stage of the work. It applies when the work is done for the first time and when it is done for the hundredth time, because the stage exists to make the hundredth time as careful as the first. It does not apply where the work is a one-off improvisation with no need for checking or record-keeping; there, a lighter method is honest and this stage would be waste. Demo

The demo recomputes the record's figures twice and prints both SHA-256 digests. Run it with node demo.js. Its output was verified byte-identical to the record's expected output at build time.

import hashlib
figures = {"files_filed": 48, "files_shared": 48, "models_opened": 36, "originals_changed": 0}
keys = sorted(figures)
total_a = sum(figures[k] for k in keys)
total_b = 0
for k in keys:
    total_b += figures[k]
d1 = hashlib.sha256(str(total_a).encode()).hexdigest()
d2 = hashlib.sha256(str(total_b).encode()).hexdigest()
print("total=" + str(total_a))
print("digest_a=" + d1)
print("digest_b=" + d2)
print("match=" + str(d1 == d2))
