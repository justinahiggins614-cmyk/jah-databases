DESCRIPTIONS
The cache plan decides what each local machine keeps on its own disk: the models it runs often, the data it uses daily, and nothing it does not need. Local disks are small, so the plan is strict: a model is cached only if the machine has run it in the last month, and the cache is cleaned every week. The plan lists what is cached, how big it is, and when it was last used, so the manager can see at a glance what is taking up space. When the disk fills, the manager removes the least-used item first and tells the user what was removed. Nothing is cached that the user marked private without their say-so, and the cache is never treated as the only copy of anything important. The Local Cache and Storage Plan stage works through 4 parts: Cache list; Usage dates; Cleaning schedule; Removal log. Each part is named, tested, and filed, so the work can be checked by a stranger. This record specifies the stage completely: what it is for, how it is done, how it is tested, what it costs in time and attention, and what can go wrong. The specification is written for a builder who has never done this stage before, and for a reviewer who must judge whether it was done properly. Inside the Cloud-to-Local AI Management Portal, Local Cache and Storage Plan sits between the stages that come before it and the stages that come after it, and it must fit both: what it receives must be in the shape it expects, and what it hands on must be in the shape the next stage expects. WORKFLOW
Problem: The problem Local Cache and Storage Plan solves is simple to state and hard to do well: Keeping the models and data a local machine needs, close at hand. Without this stage, the work goes wrong in a particular way. The failure shows up late, when it is expensive to fix, and it shows up as a surprise, because nothing was recorded that would have warned anyone. The stage exists to move the failure earlier, where it is cheap, and to make it visible, where it can be fixed. The problem is not that people are careless; it is that a job with many parts and many hands needs a fixed shape, or the parts drift apart. Local Cache and Storage Plan is that fixed shape for this part of the work.
Solution: The worked solution runs in 5 steps, in order. step 1: Cache only models run in the last month; step 2: List what is cached, its size, and last use; step 3: Clean the cache weekly; step 4: Remove the least-used item first; step 5: Tell the user what was removed. Each step has a visible result: something written, something checked, or something handed on, so the stage can be stopped and inspected at any point. The steps are done by the person or program named in the record, and each step is checked before the next begins, because a mistake carried forward is a mistake multiplied. The parts of the stage are: Cache list; Usage dates; Cleaning schedule; Removal log. When a step fails, the worker stops, fixes the failure, and re-runs the step; the stage never skips a failed step and hopes the next one covers it. The whole method is written so that two workers following it would produce the same result, and a reviewer following it could find where a result came from.
Answer: The answer this stage delivers is a finished piece of work that the next stage can use without asking questions: the Local Cache and Storage Plan is complete, checked, and filed. When those checks pass, the stage is done, and the proof is the record itself — the checks, the dates, and the names.
