JAH-KW-CHAM-000001 — Close enough counts — the chamfer recipe

Template matching demands pixel-perfect agreement; chamfer matching settles for close. The trick is the distance transform: before any matching happens, every pixel in the scene is labeled with its distance to the nearest edge pixel — 0 on an edge, 3 one step away, 4 diagonally (in the 3-4 chamfer metric). Then matching a template means laying its edge points over this map and averaging the numbers they land on. A template edge sitting exactly on a scene edge contributes 0; one pixel off contributes 3; the average is the score.

This forgiving arithmetic is the whole point. A hand-drawn template never aligns perfectly with a photographed object — edges shift a pixel here and there — and binary template matching (record: template-matching-recognition #4's SSD) punishes every shift maximally. Chamfer matching prices the shift instead of punishing it: one pixel off costs 3, not infinity. The matcher degrades gracefully with misalignment, which is why it survived from Barrow, Tenenbaum, and colleagues' 1977 parametric correspondence work into modern pedestrian detectors.

The demo builds a square outline, computes its 3-4 distance transform with the classic two-pass algorithm, and slides a corner template over it. At the true corner (3, 3) every template edge lands on distance 0: score 0.0, perfect. One pixel off, the score is 2.4; two pixels off, 4.8. The score is a ruler, not a switch — and the knowing-when bar sits at 1.5 per edge pixel.

The recognition principle

Which kernels feed it
Binary edge maps from the nine-number kernels; the distance transform is computed once per image.
The recipe
Transform the scene's edge map into a distance map (every pixel knows its distance to the nearest edge). Slide the template's edge points over it; the score is the average distance. Zero is perfect; small is good.
The knowing-when rule
FOUND iff best_score <= TAU (here 1.5 distance units per edge pixel): the template's edges must lie near real edges ON AVERAGE. Near-misses are forgiven; far-misses are not.
Used by (Tier-2/Tier-3 finders)
corner-finder, polygon-finder, car-finder, house-finder

def convolve(image, kernel):
    kh, kw = len(kernel), len(kernel[0])
    rows, cols = len(image), len(image[0])
    out = []
    for i in range(rows - kh + 1):
        r = []
        for j in range(cols - kw + 1):
            s = 0
            for a in range(kh):
                for b in range(kw):
                    s += kernel[a][b] * image[i + a][j + b]
            r.append(s)
        out.append(r)
    return out

def chamfer_dt(edge):
    INF = 10**9
    h, w = len(edge), len(edge[0])
    d = [[0 if edge[i][j] else INF for j in range(w)] for i in range(h)]
    for i in range(h):
        for j in range(w):
            if i > 0: d[i][j] = min(d[i][j], d[i-1][j]+3)
            if j > 0: d[i][j] = min(d[i][j], d[i][j-1]+3)
            if i > 0 and j > 0: d[i][j] = min(d[i][j], d[i-1][j-1]+4)
            if i > 0 and j < w-1: d[i][j] = min(d[i][j], d[i-1][j+1]+4)
    for i in range(h-1, -1, -1):
        for j in range(w-1, -1, -1):
            if i < h-1: d[i][j] = min(d[i][j], d[i+1][j]+3)
            if j < w-1: d[i][j] = min(d[i][j], d[i][j+1]+3)
            if i < h-1 and j < w-1: d[i][j] = min(d[i][j], d[i+1][j+1]+4)
            if i < h-1 and j > 0: d[i][j] = min(d[i][j], d[i+1][j-1]+4)
    return d
def chamfer_score(dt, T, i, j):
    return sum(dt[i+a][j+b] for (a, b) in T) / len(T)

JAH-KW-CHAM-000002 — The 3-4 chamfer metric — distances without a square root

True Euclidean distance needs a square root per pixel — expensive in 1977, and still annoying at scale. The chamfer 3-4 metric fakes it with integers: moving orthogonally costs 3, moving diagonally costs 4. A diagonal step covers sqrt(2) ~= 1.414 pixels and costs 4/3 ~= 1.333 — within 6% of truth. An orthogonal step covers 1 pixel and costs exactly 3/3 = 1. Distances come out in units of 'third-pixels', close enough for every matching decision, computable with nothing but addition and min.

The two-pass algorithm is the elegant part. Sweep top-left to bottom-right, letting each pixel inherit the best path from above and left; then sweep back, inheriting from below and right. After two passes every pixel knows its cheapest path to the nearest edge — a dynamic-programming wavefront, no square roots, no floating point. Borgefors' 1986 analysis made it the standard; the 3-4 weights are the sweet spot between the crude 1-1 cityblock and the costly exact Euclidean.

The demo drops a single edge pixel into a 7x7 field and prints the transform: 0 at the pixel, 3 on the four orthogonal neighbors, 4 on the diagonals, 6 two steps orthogonally, 7 at the knight's move (3+4). Read the rings: integer arithmetic drawing Euclidean circles. Every later chamfer score in this database is measured in these units.

The recognition principle

Which kernels feed it
Any binary edge map; the metric is a property of the transform, not the source.
The recipe
Forward pass top-left to bottom-right, then backward: each pixel takes the min of its neighbors' distances plus the step cost (3 orthogonal, 4 diagonal). Two passes propagate every distance.
The knowing-when rule
The metric underwrites every later gate: scores are in units of ~3x pixels, so TAU values transfer across images. A principled unit beats a magic number.
Used by (Tier-2/Tier-3 finders)
corner-finder, polygon-finder, car-finder, pedestrian-finder

JAH-KW-CHAM-000003 — The chamfer gate — score per edge pixel, decided

A score is not a decision — the lane's refrain, now in distance units. The chamfer gate has the same two-gate shape as the correlation gate: the best score must be absolutely good (at most 1.5 distance units per template edge — roughly half a pixel of average misalignment) and relatively best (a full unit better than the runner-up, so the winner is not perched on a knife edge). Mirror image of the NCC rule, with the inequalities flipped because distance runs the other way.

The per-edge-pixel normalization is what makes one TAU work for all templates: a 5-edge corner and a 50-edge car silhouette share the same bar, because both scores are averages. Without the division, big templates would need big bars and the threshold would be a per-template tuning exercise. With it, 1.5 means 'half a pixel off on average' for everything — a physical statement, not a magic number.

The demo scores a 4-edge bar template at three placements: exactly on the bar (0.0 — FOUND), shifted one pixel (1.8 — REJECT, over the bar), and in an empty region (9.0 — REJECT). The middle case is the instructive one: one pixel off on every edge is visibly close, and the gate still says no. Close enough has a number, and the number is 1.5.

The recognition principle

Which kernels feed it
Chamfer scores from the distance transform; TAU is set in 3-4 units per template edge.
The recipe
Score every placement; the best must clear an absolute bar (score <= 1.5 per edge pixel) AND beat the runner-up by a margin. Same two-gate shape as correlation, in distance units.
The knowing-when rule
FOUND iff (best <= 1.5) and (runner_up - best >= 1.0): close enough, and clearly closer than the alternatives. Distance gates mirror similarity gates.
Used by (Tier-2/Tier-3 finders)
corner-finder, box-finder, car-finder, house-finder

JAH-KW-CHAM-000004 — Occlusion-robust by construction — half the template can go missing

Occlusion is vision's constant companion — the trash can eats the car's wheel, the hand covers the face's mouth — and chamfer matching handles it with a change of averaging. The plain average lets missing edges vote huge distances and wreck the score; the robust version averages only over the edges that found something nearby (or truncates each edge's contribution at a cap). The occluded edges are simply not counted. The visible 60% of a car is still unmistakably a car.

This is the same graceful degradation as the feature hierarchy's partial composition (record: feature-hierarchy-recognition #3), arrived at from the opposite direction: there, missing parts dilute a sum; here, missing edges are excluded from an average. Both say the same thing — decide on the evidence you have, not the evidence you wish for. Gavrila's pedestrian detector (1999) made this the practical reason chamfer matching survived into the real-time era: pedestrians are always half behind something.

The demo occludes two of the corner template's five edges (a box covers them; their distances read 12+) and scores both ways. Plain average: 5.4 — REJECT, the occlusion vetoes a plainly visible corner. Robust average over the three visible edges: 1.0 — FOUND. Same evidence, honest arithmetic, opposite verdicts. The averaging is the algorithm.

The recognition principle

Which kernels feed it
Partial edge evidence; the score normalizes by the edges actually tested.
The recipe
Match the template's edges against the distance map, but average only over the edges that land near something (or use a robust truncated average). Missing edges dilute the score instead of vetoing it.
The knowing-when rule
FOUND iff the robust average over the best-matching 70% of edges <= TAU: the decision follows the visible evidence and ignores the occluded part.
Used by (Tier-2/Tier-3 finders)
car-finder, pedestrian-finder, face-finder, cat-finder

JAH-KW-CHAM-000005 — Hierarchical chamfer — coarse distance maps, fine verdicts

The pyramid from the template-matching database ports to chamfer matching unchanged — it is a search strategy, not a score. Downsample the edge map by 2, run the two-pass transform on the small version, score the (also downsampled) template cheaply, and promote only the placements that look plausible when small. The strict 1.5-per-edge gate applies only to the survivors at full resolution. Gavrila's real-time pedestrian system ran exactly this: coarse distance maps over image pyramids, fine verification on candidates.

Distance scores pyramid particularly well, because downsampling a distance map is meaningful — a coarse distance of 6 means 'about two pixels away at full resolution', no recalibration needed. The units scale with the pyramid level, so the loose upstairs gate (3.0 coarse units = 1.5 full-res units) is the same physical bar. Suspicion upstairs, conviction downstairs, one ruler throughout.

The demo hides a corner in a 16x16 edge scene and counts: brute force scores 196 placements at full cost; the pyramid scores 49 coarse, promotes 2, and verifies 18 fine placements. Same winning placement, same 0.0 score, roughly a third of the work. The Tier-3 finders need this — their templates are big and their scenes are bigger.

The recognition principle

Which kernels feed it
Distance transforms at multiple resolutions; the pyramid is a search strategy over any score.
The recipe
Downsample the edge map, transform coarse, score cheaply, promote the best few placements, verify at full resolution. Loose gate upstairs, strict gate downstairs — same as correlation's pyramid.
The knowing-when rule
Promote iff coarse_score <= 3.0 (loose); FOUND iff fine_score <= 1.5 with margin (strict). Suspicion upstairs, conviction downstairs.
Used by (Tier-2/Tier-3 finders)
car-finder, pedestrian-finder, face-finder, house-finder

JAH-KW-CHAM-000006 — Directed chamfer — orientation matters

Plain chamfer matching is orientation-blind: a horizontal template edge lying on a vertical scene edge scores 0 — perfect — even though the edges cross at right angles and agree on nothing but position. In cluttered scenes this blindness manufactures false matches out of edge soup. The directed chamfer (Olson and Huttenlocher's Hausdorff line of work, 1997) fixes it by splitting the distance transform per orientation: horizontal scene edges feed one map, vertical edges another, and each template edge consults only the map matching its own direction.

A template edge landing on a perpendicular scene edge now finds no nearby same-orientation edge and pays full distance — the orientation mismatch is priced, not ignored. The extra cost is one more transform per orientation bucket (usually 4-8), which the two-pass algorithm handles cheaply. What you buy is discrimination: in the demo, the undirected score cannot tell a horizontal bar from a vertical one, and the directed score separates them by 6 full units.

The demo builds horizontal and vertical bar scenes, transforms each orientation separately (simplified to H/V buckets), and scores a horizontal template placed at (4, 2). Directed on the horizontal scene: 0.0 — FOUND, oath kept. Undirected on the vertical scene: 3.0 — position alone scores, and a loose gate might bite. Directed on the vertical scene: 99.0 — the horizontal map is empty, no horizontal edges exist anywhere, correctly REJECTED. The Tier-3 pedestrian and car finders live on this distinction; in street clutter, orientation is half the evidence.

The recognition principle

Which kernels feed it
Edge maps WITH gradient direction (the nine-number kernels give orientation for free).
The recipe
Split the distance transform by edge orientation (horizontal vs vertical maps). Each template edge consults the map matching its own direction; mismatched orientations pay a penalty instead of scoring 0.
The knowing-when rule
FOUND iff directed_score <= TAU: position AND orientation must agree. The bar is the same 1.5 — now in position-orientation units.
Used by (Tier-2/Tier-3 finders)
pedestrian-finder, car-finder, face-finder, box-finder

JAH-KW-CHAM-000007 — The clutter failure — when close-enough is too forgiving

Chamfer matching's forgiveness is also its failure mode. In a cluttered scene — foliage, a crowd, a textured wall — edges are everywhere, so the distance transform is near-zero everywhere, so every template placement scores well. The corner template finds a 'corner' in the leaves with score 1.2, the gate says FOUND, and the detection is a phantom. The score did not lie; the scene made the question unanswerable. Close enough, applied to edge soup, means everything matches.

The honest response has three parts. First, diagnose: when the best score, the runner-up, and the median are all low, the scene is saturated and no placement is meaningful — report UNMATCHABLE, not the least-bad location. Second, tighten: directed chamfer (record 6) restores discrimination because clutter edges point every which way while the template's orientations are coherent. Third, raise the bar: in known clutter, demand 1.0 instead of 1.5 and a fatter margin.

The demo scatters random edge clutter and scores the corner template across the field: the best phantom hits 1.2 and the plain gate fires — FALSE FOUND, shown without flinching. Then the saturation check runs: median score 1.8, best 1.2 — the field is saturated, verdict revised to UNMATCHABLE. Every principle in this lane shows its failure; this is chamfer's.

The recognition principle

Which kernels feed it
Cluttered edge maps: foliage, texture, crowds — anywhere edges are dense and meaningless.
The recipe
Run the standard gate; when it fires on clutter, diagnose: the distance map is near-zero everywhere, so EVERY template scores well. The score has lost its discrimination.
The knowing-when rule
In clutter, TIGHTEN: require directed_score <= 1.0 AND a margin over the runner-up of 1.5. If the gate still fires everywhere, the scene is unmatchable — say so.
Used by (Tier-2/Tier-3 finders)
pedestrian-finder, car-finder, cat-finder, face-finder

JAH-KW-CHAM-000008 — Who uses chamfer matching — the principle's place in the R24 chain

Chamfer matching is the Tier-0 principle for finders whose targets are known shapes photographed imperfectly. The corner finder prices corner templates against edge maps (record 1, live). The polygon and box finders price outline templates, then confirm with contour fingerprints from the sibling database. The Tier-3 car and pedestrian finders are the classic customers: fixed silhouettes, endless occlusion, real-time budgets — robust averaging (record 4) plus pyramids (record 5) plus directed scores (record 6) is their whole stack.

Where chamfer hands off: when the target's edges scatter too widely for any placement to score well, the finder graduates to Hough voting (scattered pixels electing shapes) or to feature hierarchies (parts, not outlines). Chamfer wants the shape mostly where the template says; voting wants only enough pixels to agree; hierarchies want only the parts. Three forgivenesses, three databases, one recognition layer.

The demo prints the borrowing table: finder, what it prices, and its bar character. One distance transform, eight pricers — and the same gate at the end of every search: close enough, clearly closer than the alternatives, or honest silence.

The recognition principle

Which kernels feed it
Edge maps (directed variants need gradient orientation); the transform is computed once and shared.
The recipe
Each finder picks its template edges, its orientation buckets, its robust averaging, and its bar — then prices every placement and gates the best.
The knowing-when rule
The finder's knowing-when IS this database's gate (record 3), tightened for clutter (record 7): directed score <= bar with margin, or honest UNMATCHABLE.
Used by (Tier-2/Tier-3 finders)
corner-finder, polygon-finder, box-finder, car-finder, pedestrian-finder, face-finder, house-finder, cat-finder
