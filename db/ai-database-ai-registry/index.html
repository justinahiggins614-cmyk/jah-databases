The Database AI Registry is the master list of every database AI in the network, one entry per AI, recording what the AI is responsible for, what it can answer, and where its records live. A question or a file request first consults the registry, so the network can route it to the right AI instead of guessing. The registry is itself a database, so it can be searched, checked, and cited like any other record in the network.

As the network grew past a handful of databases, each with its own specialist AI, a single list became necessary so that no AI was lost or duplicated. The registry was designed as that list, kept in the same full-record form as the databases it describes. This record does not state a creation date.

A registry works by giving every AI a stable identity entry with its name, its database, its capability profile, and its access interface, so a lookup returns exactly one responsible AI for a given database or file. Because the entries are full records, they can be validated for uniqueness and completeness before any routing decision uses them. The registry also carries a file-to-AI mapping: each file in the network is listed with the database AI responsible for it, so a file request is answered by the AI that owns that file, and the mapping is checked against the registry whenever a new file is added.

A routing step compares the question with the profiles and picks the AI whose profile covers the question. A Database AI Query Router reads an incoming question and sends it to the database AI whose capability profile covers it, instead of asking every AI in the network. The router returns the answer with the name of the AI that gave it, so the asker knows who answered. If no AI covers the question, the router says so and lists the nearest AIs that might help.

Query routing was designed when the network held enough database AIs that asking all of them for every question became wasteful. The router keeps a copy of every capability profile and matches the question against them. This record does not state a creation date.

A router works by comparing the words and the subject of the question with the capability profiles in the registry, scoring each AI for coverage, and sending the question to the highest-scoring AI. If the chosen AI cannot answer, the router tries the next best AI and records the attempt. The routing decision is itself recorded, so a wrong route can be traced and corrected.

A Database AI File Router reads a request for a file and sends it to the database AI responsible for that file, using the registry's file-to-AI mapping. The mapping lists each file with the AI that owns it, so the router never has to search the whole network to find the right owner. If a file has no owner in the mapping, the router says so instead of returning a file from the wrong database.

File routing was designed alongside the registry, because files and questions need different routing: a question matches a capability, while a file matches an owner. The file-to-AI mapping is the registry's answer to the ownership question, kept as a checked list inside the registry record. This record does not state a creation date.

A file router works by looking up the requested file in the file-to-AI mapping, which pairs every file path with exactly one responsible database AI, and then asking that AI for the file. When a new file is added to a database, its mapping entry is added at the same time, so the mapping never lags behind the files. A request for a file with no mapping entry is reported as unmapped, and the missing entry is logged for the registry to fix.

A Database AI Knowledge Loader is the component that loads a database's records into its AI so the AI can answer from them. It reads the database's full records, keeps their text, their citations, and their structure, and hands them to the AI in a form the AI can search. The loader never invents content: everything the AI knows comes from the loaded records.

Knowledge loading was designed so that each database AI answers only from its own database, instead of from a general pool of text. The loader reads the same full records a person reads, so the AI and the person see the same facts. This record does not state a creation date.

A loader works by reading each record file, splitting it into its fields, and indexing the text so the AI can find the relevant record for a question. When the database gains new records, the loader adds them without reloading the whole database. If a record is removed or corrected, the loader updates the index, so the AI never answers from a record that no longer exists.

A Database AI Retrieval Engine finds the records that answer a question, ranking them by how closely they match the question's subject and words. It returns the best records with their citations, and it never returns a record it cannot cite. The engine works over the AI's own database only, so its answers stay inside the knowledge the AI is responsible for.

Retrieval engines were designed to replace guessing: instead of the AI answering from memory alone, the engine fetches the records first and the answer is built from what was fetched. The engine's ranking rules are written in the open, so a result can be explained. This record does not state a creation date.

A retrieval engine works by turning the question into search terms, matching those terms against the loaded records, and scoring each match on word overlap and subject fit. The top records are handed to the AI, which composes the answer from them and attaches their citations. If no record scores above the minimum, the engine reports no match instead of returning a weak record.

Cross-references were designed because knowledge in the network is spread across many databases, and a single database rarely tells the whole story. The tool keeps the link and its reason together, so a bad link can be challenged. This record does not state a creation date.

A cross-reference tool works by comparing a record's subject, names, and identifiers with records in other databases, and by proposing links only where the match is exact on an identifier or strong on subject and wording. Each proposed link is stored with its reason, and a link with no reason is refused. Readers follow a link to the other record and can follow it back, because every link is two-way.

A Database AI Handoff Protocol is the agreed way one database AI passes a question to another when the question belongs to the second AI's database. The handoff carries the question, the records already consulted, and the reason for the pass, so the receiving AI does not start from nothing. The asker is told that a handoff happened and which AI answered in the end.

The handoff protocol was designed because a question often starts with the wrong AI and only becomes clear after the first AI has looked at it. The protocol keeps the work done so far, so the second AI does not repeat it. This record does not state a creation date.

A handoff works by packaging the original question, the records already retrieved, and the reason the first AI could not answer into a single handoff message, and sending it to the AI named by the router. The receiving AI continues from the packaged records instead of re-running the same search. The full chain of handoffs is recorded with the final answer, so the path the question took can be traced.

The Model Card Format for Database AIs is the standard form in which a database AI's model is described: its name, its version, its intended use, its limits, and the data it was loaded from. Every model card follows the same headings in the same order, so two cards can be compared side by side. A card never claims what the model cannot do.

The model card format was designed so that model information is comparable across the whole network, instead of each AI describing its model in a different way. The format lists facts and limits together, so a capability is always read next to its limit. This record does not state a creation date.

A model card format works by fixing the headings a card must carry — identity, intended use, limits, training and loading data, and evaluation — and by requiring each heading to be filled in plain sentences. A card missing a heading is incomplete and is not published. Because every card shares the same headings, a reader can find the same fact in the same place on any card.

Per-AI Model Cards are the individual model cards, one for each database AI, written in the network's model card format. Each card names the AI it belongs to, the model behind that AI, and the limits of that model on that AI's database. The cards are kept in the registry, so a reader can go from an AI to its card in one step.

Per-AI model cards were designed so that model facts are never separated from the AI they belong to: one AI, one card, kept together. The cards are written when the AI is registered and rewritten when its model changes. This record does not state a creation date.

A per-AI model card works by filling in the standard format with the facts of one AI and its model: the AI's name and database, the model's name and version, the intended use, the known limits, and the records the model was loaded from. When the model changes, the old card is kept and a new card is written, so the history of the AI's models is preserved. A card is checked against the AI's live behaviour before it is published.

Model Capability Mapping links each capability a database AI offers to the model feature that provides it, so a reader can see which part of the model does which job. The mapping is a table: capability, model feature, and the evidence that the feature provides it. A capability with no mapped feature is listed as unmapped, never invented.

Capability mapping was designed to make model claims checkable: instead of saying a model can do something, the mapping names the feature that does it. The mapping is kept with the model card, so the claim and its evidence sit together. This record does not state a creation date.

A capability map works by taking each capability in the AI's profile and finding the model feature that supplies it, recording the pair with a short note on the evidence. Capabilities that cannot be tied to a feature are marked unmapped and are not advertised as model capabilities. The map is re-checked whenever the model or the profile changes, so a stale link cannot survive an update.

Model Version Tracking records every version of every model used by the network's database AIs, in order, with the date of entry and the reason for the change. A tracking entry names the model, the old version, the new version, and which AIs moved to the new version. The chain of versions is never broken and never rewritten.

Version tracking was designed so that a change in an AI's behaviour can be traced to a model version change, and so that an old answer can be matched to the version that gave it. Each version is a full record, kept in order. This record does not state a creation date.

Version tracking works by writing a new entry for every model change, naming the predecessor version and the reason for the change, and by recording which AIs adopted the new version and when. Answers carry the model version that produced them, so a later correction can be matched to the answers it affects. A tracking entry that does not name its predecessor is refused, keeping the chain complete.
