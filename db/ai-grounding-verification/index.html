Grounding verification is the independent check of whether an outside AI's answer actually matches a real JAH record. It takes the claims in an answer, finds the records they should rest on, and reports which claims the records support and which they do not. The check is independent because it reads the records itself instead of trusting the answer's own citations.

Checking answers against source records is a standard verification practice: a claim is only as good as the record behind it. Grounding verification applies that practice to AI answers about the JAH network, using the network's own records as the ground truth. This record does not state a creation date for the practice.

The check works by splitting an answer into individual claims, then searching the JAH records for each claim's subject, numbers, and wording. A claim that matches a record is grounded; a claim with no matching record is flagged as unsupported. The result is a score and a list of which claims passed and which failed, so the reader can see exactly where the answer stands.

Worked example: 41 of 50 = 41/50 x 100 = 82.0%. Remaining: 50 - 41 = 9.

The grounding score is a number from 0 to 100 that states how much of an answer the JAH records support. A score of 100 means every claim in the answer matches a record; a score of 0 means none of them does. The score is computed as grounded claims divided by total claims, multiplied by 100, so it is always a plain percentage.

Scores from 0 to 100 are a common way to summarise a pass rate in one number, and the grounding score follows that convention. It was defined for this database so that grounding results from different answers and different outside AIs can be compared on the same scale. This record does not state a creation date for the scale.

The score works because it turns a claim-by-claim check into a single comparable number without hiding the detail: the report behind the score still lists every claim and its verdict. A high score with a short answer and a high score with a long answer both mean the same thing — the checked claims matched records. The scale is fixed at 0 to 100 so that no answer can score above 100 or below 0.

Worked example: 85 of 100 = 85/100 x 100 = 85.0%. Remaining: 100 - 85 = 15.

Answer-vs-record comparison is the core step of grounding verification: each statement in an answer is placed beside the JAH record it should rest on, and the two are compared word by word and number by number. Where the statement and the record agree, the statement is grounded; where they differ, the difference is recorded as a mismatch. The comparison is done on the text and numbers themselves, not on how confident the answer sounds.

Comparing a statement with its source record is the oldest verification step there is: the source is the authority and the statement must match it. This record applies that step to AI answers, one statement at a time, against JAH records. This record does not state a creation date for the method.

The comparison works by extracting the checkable parts of a statement — names, dates, counts, and quoted wording — and looking each one up in the record. Exact matches pass; close matches are marked as partial and listed for a human to judge; contradictions fail. Because the check is per statement, one wrong statement does not condemn a whole answer, and one right statement does not rescue it.

Worked example: 54 of 60 = 54/60 x 100 = 90.0%. Remaining: 60 - 54 = 6.

An evidence package check verifies that an answer comes with the evidence it needs: the record identifiers, the quoted passages, and the links that let a reader open the records for themselves. The check lists every item the package should contain and marks each one present or missing, so an answer that cites nothing is scored as unevidenced even if its words sound right. A package with all items present passes the check.

Evidence packages are the standard way a claim shows its working: the reader should be able to follow the citation back to the record. This record defines the package check for grounding verification, so that an answer's evidence can be graded separately from its wording. This record does not state a creation date for the check.

The check works from a fixed list of required items — record identifier, quoted passage, and a working link to the record — and tests each claim's evidence against that list. An item is present only if it names a real record that can be opened; a link to a page that does not exist counts as missing. The result is a count of present items against required items, which feeds the overall grounding score.

Worked example: 22 of 24 = 22/24 x 100 = 91.7%. Remaining: 24 - 22 = 2.

Unsupported claim detection finds the claims in an answer that no JAH record supports. A claim is unsupported when the records contain nothing that states it, or when the records state the opposite; either way the claim is flagged and quoted in the report so the reader can see exactly what was not supported. Detection does not judge whether the claim might be true somewhere else — it judges only whether the JAH records support it.

Flagging unsupported claims is the point of grounding verification: an answer can be fluent and confident while containing claims its sources never made. This record defines detection as a separate step so that unsupported claims are counted and shown, not averaged away. This record does not state a creation date for the method.

Detection works by running each claim through the record search and marking the ones with no matching record. A claim that partially matches is marked partial rather than unsupported, so the report distinguishes a claim with weak support from a claim with none. The unsupported count is then reported as a number and a percentage of all claims checked.

Worked example: 6 of 40 = 6/40 x 100 = 15.0%. Remaining: 40 - 6 = 34.

A citation accuracy check verifies that every citation in an answer points to a real JAH record and says what that record actually says. It checks three things: the cited record exists, the quoted words appear in it, and the citation's claim matches the record's meaning. A citation that points nowhere, quotes words the record does not contain, or twists the record's meaning fails the check.

Citations are only useful when they can be followed: a citation to a record that does not exist, or to words the record never said, misleads the reader. This record defines the accuracy check so that citations are graded on what they point to, not on how formal they look. This record does not state a creation date for the check.

The check works by opening each cited record and comparing the citation's identifier, quotation, and claim against it. An identifier that matches no record fails; a quotation that does not appear in the record fails; a claim that the record contradicts fails. Citations that pass all three checks are counted as accurate, and the accurate share is reported as a percentage.

Worked example: 27 of 30 = 27/30 x 100 = 90.0%. Remaining: 30 - 27 = 3.

Source relevance scoring rates how closely each source an answer cites actually relates to the question asked. A source scores high when it is about the same subject, the same record kind, and the same database the question concerns; a source about an unrelated subject scores low even if it is a real record. The score for an answer is the share of its sources that are relevant to the question.

Relevance is separate from accuracy: a citation can be accurate yet irrelevant, quoting a real record that has nothing to do with the question. This record defines relevance scoring so that padding an answer with unrelated real records does not raise its grounding result. This record does not state a creation date for the method.

Scoring works by comparing each cited source's subject, record kind, and database against the question's subject. Sources matching on all three count as relevant; sources matching on none count as irrelevant; partial matches count as partial. The relevant share is reported as a percentage, alongside the list of sources that scored low.

Worked example: 20 of 25 = 20/25 x 100 = 80.0%. Remaining: 25 - 20 = 5.

Evidence freshness scoring rates how current the records behind an answer are. A record scores as fresh when its last-verified date is recent and its counts match the current manifest; a record whose counts have moved on, or whose verification date is old, scores lower. The freshness score for an answer is the share of its evidence that is current.

Freshness matters because the JAH network grows: a record count quoted from an old manifest can be correct for its date and wrong today. This record defines freshness scoring so that an answer built on stale records is marked down even when its citations were once accurate. This record does not state a creation date for the method.

Scoring works by reading the last-verified date on each cited record and comparing the record's stated counts with the current live manifest. Evidence that matches the current manifest counts as fresh; evidence that differs counts as stale; evidence with no date at all counts as undated. The fresh share is reported as a percentage, with stale items listed by name.

Worked example: 15 of 18 = 15/18 x 100 = 83.3%. Remaining: 18 - 15 = 3.

A contradiction check looks for statements inside one answer that disagree with each other, and for statements that disagree with the JAH record they cite. Two statements contradict each other when both cannot be true at once, for example when one gives a count of 24 and another gives a count of 30 for the same database. Every contradiction found is quoted in the report with both statements side by side.

Contradictions are a strong signal that an answer was assembled without checking: a careful answer does not state two different numbers for the same fact. This record defines the contradiction check as a separate step so that internal disagreement is caught even when each statement alone looks plausible. This record does not state a creation date for the check.

The check works by collecting every number and factual claim in the answer and grouping them by subject, then comparing the values inside each group. Two different values for the same subject are flagged, and each flagged pair is also checked against the record to see which value, if either, the record supports. The contradiction count is reported as a number and as a share of all statements checked.

Worked example: 3 of 45 = 3/45 x 100 = 6.7%. Remaining: 45 - 3 = 42.

Multi-source comparison checks a claim against more than one JAH record before calling it grounded. A claim confirmed by two or more independent records is stronger than a claim confirmed by one, and a claim confirmed by one record but contradicted by another is flagged for a human to judge. The comparison reports how many sources agree, how many disagree, and how many say nothing on each claim.

One source can be wrong, out of date, or misread, so a second source is the simplest way to raise confidence. This record defines multi-source comparison for grounding verification, so that a claim is not called grounded on a single match alone where more records exist. This record does not state a creation date for the method.

The comparison works by searching all JAH records for each claim, not just the first match, and sorting the matches into agreeing, disagreeing, and silent. A claim with two or more agreeing sources and no disagreeing source counts as confirmed; a claim with any disagreeing source counts as contested. The confirmed share is reported as a percentage of all claims checked.

Worked example: 10 of 12 = 10/12 x 100 = 83.3%. Remaining: 12 - 10 = 2.

Independent source comparison checks a claim against a source that does not come from the same place as the answer's own citation. Two records that copy each other are not independent, so the check looks for records with different provenance — a different database, a different source site, or a different record kind — before counting a claim as independently confirmed. A claim confirmed only by records that all derive from one another is marked as single-source.

Independence matters because a copied error looks like agreement: if two records share one origin, they will agree even when the origin is wrong. This record defines independent-source comparison so that agreement is only counted when the agreeing records genuinely come from different places. This record does not state a creation date for the method.

The comparison works by recording the provenance of every matching record — its database, its source, and its record kind — and grouping matches by provenance. A claim counts as independently confirmed only when agreeing records come from at least two different provenance groups. The independently confirmed share is reported as a percentage, with single-source claims listed separately.

Worked example: 16 of 20 = 16/20 x 100 = 80.0%. Remaining: 20 - 16 = 4.

Every report carries the same sections in the same order, so reports from different answers can be compared side by side. A report with a missing section is incomplete.

A fixed report format matters because grounding results are only useful when they can be compared: two reports with different shapes cannot be set side by side. This record defines the format so that every grounding check produces the same sections, whether the answer scored high or low. This record does not state a creation date for the format.

The format works as a checklist: the report writer fills each section in turn, and the reader checks that all sections are present before trusting the score. The sections are the score, the claim counts, the per-claim verdicts, the citation result, and the freshness result. Completeness is measured as sections present divided by sections required, reported as a percentage.

The grounding failure taxonomy is the fixed list of ways a grounding check can fail: unsupported claim, wrong citation, contradicted claim, irrelevant source, stale evidence, missing evidence package, and internal contradiction. Each failure type has a name, a definition, and an example, so that two checkers classifying the same failure give it the same name. The taxonomy exists so failure counts can be compared across answers and across time.

A shared list of failure types matters because without one, the same failure gets a different name every time and the counts cannot be added up. This record defines the taxonomy as seven named types, each with a definition, for use in grounding reports. This record does not state a creation date for the taxonomy.

The taxonomy works by giving the checker a fixed set of labels and a rule for choosing between them: an unsupported claim has no supporting record, a wrong citation points to a record that does not say what is claimed, a contradicted claim is denied by its own record, and so on. Failures that fit no type are marked unclassified and counted separately. Classification accuracy is measured as failures classified correctly divided by failures classified.

Worked example: 12 of 14 = 12/14 x 100 = 85.7%. Remaining: 14 - 12 = 2.

The grounding remediation loop is the process that follows a failed grounding check: the report names the failed claims, the answer is corrected against the records, and the corrected answer is checked again. The loop repeats until the answer passes or until a fixed number of rounds is reached, and each round's score is recorded so the improvement can be seen. The loop does not change the records; it changes the answer.

A failed check is only useful if it leads to a better answer, so the remediation loop turns the report into corrections and re-checks the result. This record defines the loop as a repeat of check, correct, and re-check, with a fixed round limit so it cannot run forever. This record does not state a creation date for the loop.

The loop works by taking the list of failed claims from the report, correcting each one from the record it should have matched, and running the full grounding check on the corrected answer. The new score is compared with the old score, and the loop stops when the score reaches the passing level or the round limit is reached. Success is measured as failures fixed divided by failures found, reported as a percentage.

Worked example: 8 of 10 = 8/10 x 100 = 80.0%. Remaining: 10 - 8 = 2.

The claim verification engine is the program that carries out a grounding check: it splits an answer into claims, searches the JAH records for each claim, compares claim and record, and writes the grounding report. It is a program, not a person, so it follows the same steps every time and its results can be repeated and tested. The engine described here is a design for such a program; this record does not claim it is deployed or running.

A verification engine matters because checking claims by hand is slow and inconsistent, while a program can check every claim the same way every time. This record defines the engine as a design with fixed steps — split, search, compare, report — so that an implementation can be built and tested against the test library. This record does not state a creation date for the design.

The engine works by running the four steps in order: splitting the answer into claims, searching the records for each claim, comparing each claim with its matching record, and writing the score and verdicts into the report format. Each step is deterministic, so the same answer and the same records always produce the same report. Accuracy is measured as claims verified correctly divided by claims processed, reported as a percentage.

Worked example: 470 of 500 = 470/500 x 100 = 94.0%. Remaining: 500 - 470 = 30.

Claim confidence scoring assigns each checked claim a confidence level — high, medium, or low — based on how strongly the records support it. A claim that matches a record word for word scores high; a claim that matches only in part scores medium; a claim with no matching record scores low. The confidence levels are reported alongside the grounded or ungrounded verdict, so the reader can see which verdicts are solid and which are close calls.

A verdict alone hides how close the call was: two grounded claims can rest on very different amounts of evidence. This record defines confidence scoring so that the strength of the support is shown next to the verdict, and weak support is not mistaken for strong support. This record does not state a creation date for the method.

Scoring works by grading the match between claim and record: an exact match on wording and numbers scores high, a partial match on wording or numbers scores medium, and no match scores low. The share of high-confidence claims is reported as a percentage of all claims scored, and low-confidence claims are listed for a human to review.

Worked example: 64 of 80 = 64/80 x 100 = 80.0%. Remaining: 80 - 64 = 16.

AI answer grounding testing is the full practice of putting an outside AI's answers through grounding verification on a regular basis: choosing questions, collecting answers, running the checks, and recording the scores over time. It turns one-off checks into a running record, so that whether an outside AI's answers are getting better or worse grounded can be seen from the scores. Testing covers the answers, not the AI itself, and it claims nothing about how the AI works inside.

Regular testing matters because a single answer says little: only a series of checked answers shows a pattern. This record defines the practice as a repeated cycle of questions, answers, checks, and recorded scores, using the grounding report format for every check. This record does not state a creation date for the practice.

Testing works by running the same set of questions at regular intervals, checking each answer against the JAH records, and storing the score and the per-claim verdicts. The grounded share across all tested answers is reported as a percentage, and the trend of scores over time shows whether grounding is improving. No test in this practice has been run against a live outside AI; the practice is defined here as a procedure.

Worked example: 82 of 100 = 82/100 x 100 = 82.0%. Remaining: 100 - 82 = 18.
