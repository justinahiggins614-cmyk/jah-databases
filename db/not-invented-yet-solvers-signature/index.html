How to State a Problem for a System That Does Not Exist Rank 1 · simple

Feasibility: buildable-now The method uses only writing, arithmetic, and review, all of which exist today; only discipline stands in the way.

A design method for future systems: a way of writing down a problem before any machine exists that could suffer from it, so the problem can be studied, argued about, and solved on paper first. This is a design method, not a real product.

A problem for a system that does not exist is easy to state badly: either it describes today's machine with a wish attached, or it describes a fantasy with no testable parts. Without a disciplined statement, teams argue about different machines, solutions cannot be compared, and feasibility labels become guesses. The statement must name the future system as a design, name what breaks or is missing, name who is affected, and name what would count as fixed, all without pretending the machine exists. That discipline is the missing first step of the whole program, because every later record in this database depends on a problem stated well enough to be solved.

Worked example, Signature design: the same cooling problem is stated from the machine heat budget first, then the failure, then the user, then the fixed state, so the statement can be checked against the budget line by line.

History

Stating problems before building is an old engineering habit, from bridge specifications written before any steel was cut to requirements documents for spacecraft; the habit matters more, not less, when the machine does not exist yet, because paper is the only place the problem can be examined.

Proposed solution

Sketch the design first, then read the problem off the sketch; State the break as a measurable gap, not a feeling; Name the affected user and the fixed state in the same sentence; Separate facts from guesses into two lists; Test the statement by asking a stranger to restate it.

A design classification for future-system solutions: five labels, from buildable-now to physically-unsupported, each earned by evidence written on the record. This is a design classification, not a real product.

Without a shared label set, one person's 'possible' is another person's 'impossible', and optimistic language hides real gaps. A label set by evidence lets a reader sort a whole design set by maturity at a glance, and lets a program say plainly which of its designs are near and which are far.

Feasibility: buildable-now Mapping dependencies is a writing and review method that uses only existing knowledge; it can be done for any design today.

A design method that lists, for any proposed solution, everything that must exist first: materials, physics, standards, and infrastructure, each named. This is a design method, not a real product.

A solution that does not name its dependencies looks ready when it is not. Designing a Verification Path Before the Hardware Exists Rank 4 · simple

Feasibility: research-stage Public research on simulation, prototyping, and test design exists and is published, but no complete verification-path method for unbuilt systems exists at the needed scale yet.

A design method that writes, before any hardware exists, how a solution could be tested once the system exists: simulation criteria, prototype criteria, and measurable checks. This is a design method, not a real product.

A solution with no verification path cannot be proven wrong, which means it cannot be proven right either. When the hardware does not exist, the temptation is to postpone testing until later, but later never arrives with a test list attached. A verification path written now names the simulation that would stand in for the machine, the prototype that would stand in for the full system, and the numbers that would count as passing, so that when the hardware finally exists, the test is already written. Without it, a design set grows full of solutions nobody knows how to check, and the first real test is invented in a hurry.

Worked example, Signature design: the same self-repair design is verified by a failure-first test list, where the disproving test is a fault the design cannot repair, stated before the simulation is built.

History

Writing tests before building descends from acceptance testing in software and from proof loads on bridges, where the test was agreed before the structure was trusted; applying the same order to unbuilt machines keeps the design honest while the hardware is still only paper.

Proposed solution

Start from the failure: write the test that would kill the design first; Build the simulation criteria around that failure, not around the success case; Write prototype criteria as a ladder: smallest test, then larger, then full scale; Set pass numbers before any test runs, so a good result cannot be redefined later; List the untestable parts openly, with the reason each one waits.

When a Solution Must Refuse: Physically Unsupported Claims Rank 6 · simple

Feasibility: buildable-now The refusal rule is a writing and review method that uses only existing knowledge; it can be applied to any design today.

A design rule for the whole program: when a proposed effect conflicts with established physics or has no known mechanism, the record says so plainly and keeps the solution only as a design study of what would be needed. This is a design rule, not a real product.

The hardest record to write is the one that must refuse. A design that asks a machine to think faster than light allows, or to run forever on nothing, sounds exciting, and the pressure to soften the label is real. This index gathers the whole solver method into one ordered path, so a reader can follow the method one step at a time or jump to the step their project needs. The path runs from stating a problem for a system that does not exist, through the five feasibility labels, dependency mapping, verification paths, simulation limits, refusals, research crossings, the three lane overviews, the three walls, standards, the maturity ladder, failure modes, supply chains, safety boundaries, teaching, versioning, measurement, the three cross-lane indexes, and the solver's audit. Each step links to the record that works it in full, with its own worked example and its own feasibility label, so the method can be followed in order or entered at any step.

Worked example, Signature design: the same reader follows the path once in order and then uses it as a reference, entering at the verification step when a new design needs a test list.
