JAH-KW-CONT-000001 — Contour to polygon — Douglas-Peucker finds the corners

A contour is a thousand pixels; a shape is a handful of corners. Douglas-Peucker (David Douglas and Thomas Peucker, 1973) is the bridge: give it the ordered boundary pixels and a tolerance epsilon, and it hands back the polygon. The algorithm is beautifully simple — draw a chord from the contour's start to its end, find the pixel farthest from that chord, and if it sticks out more than epsilon, it must be a real corner: keep it and recurse on the two halves. If nothing sticks out beyond epsilon, the whole stretch was just edge-filler and two endpoints suffice.

Notice what the algorithm never does: it never learns, never trains, never guesses. It is a certified simplifier — the output polygon is guaranteed to stay within epsilon of every original pixel. That guarantee is the seed of this database's knowing-when rule: a point survives exactly when its deviation exceeds epsilon, so the final vertex list is not an opinion but a measurement.

The demo traces a square with jittery midpoints (8 boundary points) and runs the closed-contour Douglas-Peucker at epsilon 0.5. The four jittered midpoints deviate only 0.3 from their chords and are discarded; the four true corners deviate 4+ and survive. Eight pixels in, four corners out: the contour has become a quadrilateral, and counting to four is the first act of shape recognition.

The recognition principle

Which kernels feed it
Ordered boundary pixel lists traced from binary edge maps (the nine-number kernels' output, linked into contours).
The recipe
Walk the contour; whenever the farthest point from the current chord sticks out farther than epsilon, keep it and recurse on both halves. What survives is the polygon: corners kept, edge-fillers discarded.
The knowing-when rule
A point is KEPT iff its deviation from the chord > epsilon. The polygon is decided when no surviving point deviates more than epsilon — the approximation is certified within tolerance.
Used by (Tier-2/Tier-3 finders)
square-finder, triangle-finder, polygon-finder, box-finder

def convolve(image, kernel):
    kh, kw = len(kernel), len(kernel[0])
    rows, cols = len(image), len(image[0])
    out = []
    for i in range(rows - kh + 1):
        r = []
        for j in range(cols - kw + 1):
            s = 0
            for a in range(kh):
                for b in range(kw):
                    s += kernel[a][b] * image[i + a][j + b]
            r.append(s)
        out.append(r)
    return out

def perp_dist(p, a, b):
    (x0, y0), (x1, y1), (x2, y2) = p, a, b
    num = abs((y2-y1)*x0 - (x2-x1)*y0 + x2*y1 - y2*x1)
    den = ((y2-y1)**2 + (x2-x1)**2) ** 0.5
    return num/den if den else 0.0

def dp_open(pts, eps):
    if len(pts) < 3:
        return pts[:]
    a, b = pts[0], pts[-1]
    dmax, idx = 0, 0
    for i in range(1, len(pts)-1):
        d = perp_dist(pts[i], a, b)
        if d > dmax:
            dmax, idx = d, i
    if dmax > eps:
        return dp_open(pts[:idx+1], eps)[:-1] + dp_open(pts[idx:], eps)
    return [a, b]

def dp_closed(pts, eps):
    n = len(pts)
    dmax, idx = 0, 0
    for i in range(1, n):
        d = ((pts[i][0]-pts[0][0])**2 + (pts[i][1]-pts[0][1])**2) ** 0.5
        if d > dmax:
            dmax, idx = d, i
    left = dp_open(pts[:idx+1], eps)
    right = dp_open(pts[idx:] + [pts[0]], eps)
    return left[:-1] + right[:-1]

print("Douglas-Peucker epsilon=0.5 -> %d vertices:" % len(poly), poly)

JAH-KW-CONT-000002 — Epsilon, the tolerance knob — one contour, three truths

Epsilon is the only knob on the Douglas-Peucker machine, and it is the whole knowing-when question in miniature. Set it near zero and the algorithm keeps everything, jitter included — eight vertices, a faithful but useless polygon. Set it enormous and it keeps almost nothing — two vertices, a line where a square was. Somewhere between lies the truth, and the sweep finds it: the vertex count drops 8 to 4 as epsilon passes the jitter size (0.3), then stays at 4 across a wide plateau, then collapses when epsilon exceeds the shape itself.

That plateau is the formal answer to 'which epsilon?'. Real corners deviate a lot (half the shape's width); jitter deviates a little (sensor noise). Any epsilon between those two scales returns the same four corners, so the choice is not fragile — pick the middle of the plateau and move on. This stability criterion generalizes far beyond contours: whenever a parameter has a plateau, the plateau is the truth.

The demo sweeps epsilon over the jittery square and prints the vertex count at each stop: 8 at 0.1, 4 at 0.5, 4 at 2.0, 2 at 10.0. The plateau at 4 is visible as a table, not an argument. Epsilon 0.5 — the middle of the plateau — is the certified choice.

The recognition principle

Which kernels feed it
Boundary pixel lists; epsilon is chosen relative to the shape's size, not the pixels' noise.
The recipe
Sweep epsilon from tiny to huge and watch the vertex count fall: tiny keeps the jitter, medium keeps the corners, huge keeps nothing. Pick the epsilon where the count stabilizes.
The knowing-when rule
The RIGHT epsilon is where the vertex count plateaus across a sweep (here 4 vertices from 0.3 to 8.0): stability across tolerance is the signal that the corners are real.
Used by (Tier-2/Tier-3 finders)
polygon-finder, square-finder, contour-finder, triangle-finder

JAH-KW-CONT-000003 — Counting vertices — three is a triangle, four is a quadrilateral, many is a circle

Before neural networks, before feature descriptors, there was counting. Three vertices is a triangle. Four is a quadrilateral — and if the four sides are equal it is a square, otherwise a rectangle. Five is a pentagon. Eight or more starts to smell like a circle, which this classifier confirms with a roundness test (record 5). It sounds too simple to work, and on clean contours it works beautifully, because Douglas-Peucker has already done the hard perceptual work of deciding what counts as a corner.

The honesty clause matters: vertex counts of 6 or 7 match no classical shape, and the classifier says 'unknown polygon' instead of forcing a wrong name. A hexagon would be a fine answer if hexagons were in the vocabulary — the classifier's vocabulary is explicit, and outside it the only truthful output is uncertainty. This is the recognition layer's contract again: a wrong name is worse than no name.

The demo builds four contours — a triangle, a square, a regular pentagon, and a 12-sided circle approximation — simplifies each at plateau epsilon, and classifies by count. All four verdicts print correctly: triangle, square, pentagon, circle-candidate. Four shapes, one integer each, zero learning required.

The recognition principle

Which kernels feed it
Douglas-Peucker polygons; the classifier reads only the vertex count plus side lengths.
The recipe
Simplify the contour, count the vertices: 3 = triangle, 4 = quadrilateral (square if sides equal, rectangle otherwise), 5 = pentagon, 8+ = circle candidate. The count IS the classification.
The knowing-when rule
DECIDE the shape name iff the vertex count falls exactly on a known integer AND the count is plateau-stable (record 2's test). A count of 6 or 7 is 'unknown polygon' — honest, not forced.
Used by (Tier-2/Tier-3 finders)
triangle-finder, square-finder, rectangle-finder, circle-finder, polygon-finder

import math
def side_lens(poly):
    n = len(poly)
    return [((poly[(i+1)%n][0]-poly[i][0])**2 + (poly[(i+1)%n][1]-poly[i][1])**2)**0.5 for i in range(n)]
def classify(contour, eps=0.5):
    poly = dp_closed(contour, eps)
    n = len(poly)
    if n == 3: return "triangle"
    if n == 4:
        s = side_lens(poly)
        return "square" if max(s)-min(s) < 0.6 else "rectangle"
    if n == 5: return "pentagon"
    if n >= 8: return "circle candidate (%d vertices)" % n
    return "unknown polygon (%d vertices)" % n

JAH-KW-CONT-000004 — Chain codes — the contour as a sentence of directions

In 1961 Herbert Freeman proposed writing a contour the way you would dictate a walk: 'east, east, north, north, west, west, south, south.' Number the eight compass directions 0 through 7 and the walk becomes a code — 0,0,2,2,4,4,6,6 for a square traced counterclockwise. The representation is tiny, exact, and beautifully structural: straight runs in the code are straight sides on the shape, and the jumps between runs are the corners.

Chain codes also solve rotation more gracefully than templates ever could. Rotate the square 45 degrees and the absolute code changes — but the DIFFERENCE code (each step minus the previous, mod 8) does not: it reads 'straight, straight, right-turn, straight, straight, right-turn...' no matter the orientation. Shape lives in the turns, not the headings. That one insight — compare turn sequences, not direction sequences — makes chain codes rotation-proof the way NCC is lighting-proof.

The demo encodes a traced square into its Freeman code, counts the straight runs (4 — four sides), and prints the difference code to show the four right turns. Then it encodes the same square traced from a different starting pixel: the absolute code rotates, the turn sequence is identical. Starting point, like orientation, washes out of the comparison.

The recognition principle

Which kernels feed it
Ordered 8-connected boundary pixels; each step becomes one of 8 direction numbers.
The recipe
Walk the boundary; record each step's direction as a number 0-7. The code's straight runs are the sides, its turns are the corners. Compare codes by rotation-normalized difference.
The knowing-when rule
Two contours share a shape iff their normalized chain codes match within a turn budget: same run lengths, same turn sequence. A square is 'four equal runs, four right turns' in any orientation.
Used by (Tier-2/Tier-3 finders)
square-finder, polygon-finder, contour-finder, box-finder

DIRS = {(1,0):0,(1,1):1,(0,1):2,(-1,1):3,(-1,0):4,(-1,-1):5,(0,-1):6,(1,-1):7}
def chain_code(pts):
    code = []
    for i in range(len(pts)):
        a, b = pts[i], pts[(i+1) % len(pts)]
        dx = (b[0] > a[0]) - (b[0] < a[0])
        dy = (b[1] > a[1]) - (b[1] < a[1])
        code.append(DIRS[(dx, dy)])
    return code

JAH-KW-CONT-000005 — Roundness by the isoperimetric ratio — the circle test

Of all closed curves with a given perimeter, the circle encloses the most area — the isoperimetric inequality, known since antiquity. Turn it into a ratio, 4*pi*area/perimeter^2, and you have a perfect circle detector: the circle scores exactly 1.0, the theoretical maximum, a square scores pi/4 = 0.785, and a long thin bar limps in near zero. One number, computed from area and perimeter alone, separates circles from everything else.

The ratio's power is its invariance: scale the shape up ten times and area grows 100x while perimeter-squared grows 100x — the ratio does not move. Rotate it, translate it, same score. For the circle finder this is the confirmation test after vertex counting raises the suspicion: '8+ vertices' says maybe-circle, 'circularity 0.97' says circle, case closed. Ellipses score slightly below 1.0 in proportion to their eccentricity, so the same number grades them too.

The demo computes circularity for three polygons — a 12-gon circle, a square, and a 6x1 bar — using the shoelace formula for area. The scores print as 0.99, 0.785, and 0.35: circle confirmed, square rejected, bar laughed out of the room. One ratio, three verdicts.

The recognition principle

Which kernels feed it
Polygons from Douglas-Peucker; area via shoelace, perimeter by summing sides.
The recipe
Compute circularity = 4*pi*area / perimeter^2. A perfect circle scores 1.0 — the maximum any shape can reach — and everything else scores less. Threshold near 0.9 to declare 'circle'.
The knowing-when rule
CIRCLE iff circularity >= 0.9: the ratio is scale-invariant, so a coin and a wheel score the same. Below 0.9, fall back to vertex counting.
Used by (Tier-2/Tier-3 finders)
circle-finder, ellipse-finder, cat-finder, face-finder

import math
def area(poly):
    return abs(sum(poly[i][0]*poly[(i+1)%len(poly)][1] - poly[(i+1)%len(poly)][0]*poly[i][1]
                   for i in range(len(poly)))) / 2
def perimeter(poly):
    return sum(((poly[(i+1)%len(poly)][0]-poly[i][0])**2 + (poly[(i+1)%len(poly)][1]-poly[i][1])**2)**0.5
               for i in range(len(poly)))
def circularity(poly):
    p = perimeter(poly)
    return 4*math.pi*area(poly)/(p*p)

JAH-KW-CONT-000006 — Convexity defects — the notches that name the shape

Vertex counting sees a star and a decagon and shrugs — both have ten corners. Convexity defects see the difference instantly. Walk a convex shape's boundary and you turn the same direction at every corner, left-left-left all the way around. Walk a star and the turns alternate: left at each point, right at each notch. Each right-turn on a left-turn walk is a concave vertex, a place where the shape caves inward — a convexity defect, in the literature's term.

The defect count is a genuine shape signature. A 5-pointed star has exactly 5 defects; an arrow has 2; a crescent has 2; a square has 0. Combined with the vertex count you get a two-number fingerprint — (10 vertices, 5 defects) is unmistakably a star — that no rotation, scaling, or translation disturbs. The Tier-2 polygon finder uses this when vertex counts collide.

The demo builds a 5-pointed star outline and a square, computes the turn sign at each vertex via the cross product, and counts the flips. Star: 10 vertices, 5 defects. Square: 4 vertices, 0 defects. Two numbers, two shapes, no confusion possible.

The recognition principle

Which kernels feed it
Douglas-Peucker polygons; the test reads the turn direction at each vertex.
The recipe
Walk the polygon and note each turn's direction (left or right). A convex shape turns the same way everywhere; every direction flip marks a concave notch — a convexity defect. Count the flips.
The knowing-when rule
STAR iff defect_count == 5 (for the 5-point family); CONVEX iff defect_count == 0. The defect count is a shape signature no vertex count can give.
Used by (Tier-2/Tier-3 finders)
polygon-finder, contour-finder, star-finder, fish-finder

def defects(poly):
    n = len(poly)
    signs = []
    for i in range(n):
        ax, ay = poly[i][0]-poly[i-1][0], poly[i][1]-poly[i-1][1]
        bx, by = poly[(i+1)%n][0]-poly[i][0], poly[(i+1)%n][1]-poly[i][1]

    return sum(1 for i in range(n) if signs[i] != signs[i-1])

JAH-KW-CONT-000007 — The approximation quality gate — certified polygons only

Douglas-Peucker promises its polygon stays within epsilon of the contour — but promises are for the algorithm's output, and the recognition layer verifies. The quality gate has two checks. First, fidelity: measure the actual maximum deviation of every original boundary point from the simplified polygon and demand it stay under epsilon. If the simplifier has a bug, or the contour was not what you thought, this catches it. Second, stability: double epsilon and recount the vertices. Real corners survive the doubling; tolerance artifacts — vertices that exist only because epsilon was small — vanish.

This is the contour database's full knowing-when rule, and it mirrors the template matcher's two gates: strong enough (fidelity), and clearly better than the alternatives (stability — the count does not wobble when the tolerance breathes). A polygon that passes both is certified: it faithfully represents the contour AND its corners are genuine features of the shape.

The demo certifies two approximations. The jittery square at epsilon 0.5: max deviation 0.3, count stable at 4 when doubled — ACCEPT. A pathological zigzag contour at a too-small epsilon: the count collapses from 9 to 4 on doubling — REJECT, corners were tolerance artifacts. The gate keeps the honest polygons and returns the rest for re-tuning.

The recognition principle

Which kernels feed it
The polygon and the original contour it claims to represent.
The recipe
Verify the certificate: measure the maximum deviation of original points from the polygon (must be <= epsilon), then double epsilon and require the same vertex count (plateau stability). Pass both or reject the polygon.
The knowing-when rule
ACCEPT the polygon iff (max_deviation <= eps) AND (count(eps) == count(2*eps)). The first gate checks fidelity; the second checks that the corners are real, not tolerance artifacts.
Used by (Tier-2/Tier-3 finders)
polygon-finder, square-finder, box-finder, house-finder

def perp_dist(p, a, b):
    (x0, y0), (x1, y1), (x2, y2) = p, a, b
    num = abs((y2-y1)*x0 - (x2-x1)*y0 + x2*y1 - y2*x1)
    den = ((y2-y1)**2 + (x2-x1)**2) ** 0.5
    return num/den if den else 0.0

def dp_open(pts, eps):
    if len(pts) < 3:
        return pts[:]
    a, b = pts[0], pts[-1]
    dmax, idx = 0, 0
    for i in range(1, len(pts)-1):
        d = perp_dist(pts[i], a, b)
        if d > dmax:
            dmax, idx = d, i
    if dmax > eps:
        return dp_open(pts[:idx+1], eps)[:-1] + dp_open(pts[idx:], eps)
    return [a, b]

def dp_closed(pts, eps):
    n = len(pts)
    dmax, idx = 0, 0
    for i in range(1, n):
        d = ((pts[i][0]-pts[0][0])**2 + (pts[i][1]-pts[0][1])**2) ** 0.5
        if d > dmax:
            dmax, idx = d, i
    left = dp_open(pts[:idx+1], eps)
    right = dp_open(pts[idx:] + [pts[0]], eps)
    return left[:-1] + right[:-1]
def max_deviation(contour, poly):
    m = len(poly)
    best = 0.0
    for p in contour:
        d = min(perp_dist(p, poly[i], poly[(i+1)%m]) for i in range(m))
        best = max(best, d)
    return best
def gate(contour, eps):
    p1, p2 = dp_closed(contour, eps), dp_closed(contour, 2*eps)
    dev = max_deviation(contour, p1)
    ok = dev <= eps and len(p1) == len(p2)
    return ok, dev, len(p1), len(p2)

JAH-KW-CONT-000008 — Who uses contour approximation — the principle's place in the R24 chain

Contour approximation is the Tier-0 principle behind every R24 finder whose target has an outline. The triangle, square, and rectangle finders ARE records 1-3: trace, simplify, count, name. The polygon finder adds chain codes (record 4) for rotation-proof comparison and convexity defects (record 6) for stars and arrows. The box finder simplifies, then checks that the quadrilateral's angles are right angles. The contour finder — Tier 2's generalist — runs the whole battery and reports the fingerprint.

The Tier-3 thing finders borrow it for silhouettes. The car finder simplifies the side silhouette and checks the fingerprint against a car-like profile; the house finder wants a pentagon-ish fingerprint (square body plus triangular roof reads as fiveish vertices with one defect pattern). Where outlines deform — a cat curled vs stretched — the finders graduate to feature hierarchies, which do not need the whole outline to agree.

The demo prints the borrowing table: finder, what it reads off the polygon, and its vocabulary. One simplifier, eight readers.

The recognition principle

Which kernels feed it
Traced contours from edge maps; the polygon is the finders' working representation.
The recipe
Each finder traces its candidate's contour, simplifies it at plateau epsilon, and reads the shape off the polygon: counts, ratios, defects. Same simplifier, different vocabularies.
The knowing-when rule
The finder's knowing-when IS this database's quality gate (record 7) plus its own shape vocabulary: the polygon must be certified AND its fingerprint must name a known shape.
Used by (Tier-2/Tier-3 finders)
triangle-finder, square-finder, rectangle-finder, polygon-finder, box-finder, contour-finder, car-finder, house-finder
