Database Builder: Command Line and Batch Use

JAH-DBBP-000006 — database builder program record

The Database Builder also works from the command line and in batches: the same job the screen does can be run without a screen, one item at a time or many at once, so that repeated work can be scripted and scheduled. Batch runs read their input from a file, write their results to a file, and report a summary line for every item — passed, failed, or held — so that a run of a thousand items is as checkable as a run of one. This record specifies the commands, their inputs, and their outputs. In this public edition the program offers 8 capabilities (generating a database from a short specification (1); creating records that pass validation on first build (2); writing the manifest entry with a free slug and ID prefix (3); checking the new database against CHECK 2 (4); producing public and Signature editions together (5); reusing the live construction-pattern database (6); an API other programs use to build databases (7); a plain-text build report readable without JavaScript (8)), 6 interfaces (Specification form — subject, record kind, and fields, in plain words; Field editor — add, name, and describe each field; Build button — one action that builds the whole database; Build report — what was built, record counts, validation result; Builder API — machine-readable database building for other programs; Plain-text mode — the build report as readable plain text), and 8 data fields (subject — what the database is about; record_kind — what sort of record it holds; fields — the named fields each record carries; slug — the database's short web-address name; id_prefix — the short code at the start of every record identifier; records — the records built, public and Signature; manifest_entry — the entry written for the manifest; validation — the CHECK 2 result for the new database). This record is number 6 of 24 in the public edition of the Database Builder database pair, and it specifies the command line and batch use topic in full — what it is, how it works, what it accepts, what it returns, and how it is tested — so that a builder can build it and a tester can verify it without guessing.
