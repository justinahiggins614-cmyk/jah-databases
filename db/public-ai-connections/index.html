ChatGPT link fetch is the method of pasting a public web address into a ChatGPT chat and asking ChatGPT to read the page through its web search or browsing tool, then answer from that page. The worked example in this record is the JAH Network thesis hub page, a plain public HTML page on GitHub Pages. The method works when the page is public and reachable by OpenAI's search tooling, and it fails honestly when it is not: a plain chat with no web tool does not follow links at all, and a share link that blocks automated readers returns nothing usable. This record documents the method exactly as the public sources describe it, with the tool requirement stated up front, so a reader can tell before trying whether their chat has what the method needs.

History

ChatGPT launched without web access, so early guides told users to copy page text by hand and paste it into the chat, because the model could only read what was put in front of it. OpenAI added web search on 31 October 2024, first for paying users and then for all logged-in users on 16 December 2024, and for everyone in supported regions on 5 February 2025, so a chat with search enabled could fetch current pages and answer with links to the sources it used. Later the agent mode added a visual and text browser that could open pages, click, and download files, and the Atlas browser put ChatGPT beside the page itself. Through every change the same rule held: the model only reads a page when a tool fetches it. The link in the chat is text until a tool acts on it, and that is the fact this record is built around.

How It Works

ChatGPT reads a pasted link only when a web tool acts on it. In a chat with Search enabled, the tool fetches the page, puts its text into the model's context, and the answer comes back with links to the sources used. In a plain chat with no tool, the pasted address stays as text: the model sees the characters of the URL and nothing of the page. The method is therefore two steps, not one: paste the address, and make sure the search or browsing tool is on. For the thesis page, the public GitHub Pages address is the one to paste, because the muse.ai share link returns 403 to automated readers and gives the tool nothing to read.

What It Needs

A ChatGPT account and a chat with the web search tool available, plus the complete public HTTPS address of the page. No key, no file, and no payment is needed for the method itself; search availability varies by plan and region, and searches count against the plan's usage limits.

What It Can Read

Public pages that serve plain HTML to automated readers, including the JAH Network thesis hub page and the llms.txt guide. It cannot read pages that need a login, pages behind a paywall, or pages whose host blocks automated readers; the muse.ai share link for the thesis is in that blocked class.

Limits

The model only knows what the tool fetched, and the search results and citations can be incomplete, outdated, or incorrect, as OpenAI's own help page states. A long page may be summarized from part of its content rather than read whole. The method gives no guarantee about which pages the search tool will fetch, and the behaviour changes as OpenAI changes the tool.

Science Proof

A language model has no browser of its own: it generates text from the tokens in its context window, and a URL pasted into that window is only characters until some other component performs an HTTP request and puts the fetched text into the context. That is why the same paste behaves differently in different chats. With a search or browsing tool active, the tool performs the request, the page text enters the context, and the model can quote and cite it. Without the tool, nothing performs the request, so the model can only reason about the URL string itself, which is why it sometimes guesses at a page's contents instead of reading them. A host that returns 403 to automated readers breaks the chain at the fetch step: the tool receives an error page instead of the content, so the model has nothing to read. The public GitHub Pages copy of the thesis works because it serves plain HTML to any requester with no login and no bot block, so the tool's request succeeds and the content enters the context.

History

The robots.txt and sitemap.xml pair is as old as the crawlable web: robots.txt tells crawlers which parts of a site they may request, and the sitemap lists the URLs a site owner wants search engines to discover. The Sitemap directive in robots.txt is the passive discovery route: a crawler that reads robots.txt learns the sitemap's location without any submission through a search console, and the sitemaps.org protocol allows the line to point at a sitemap index that itself lists several individual sitemaps. Google deprecated the standalone sitemap ping endpoint in 2023 and now recommends Search Console or robots.txt for sitemap submission. The JAH hub adopted the pair as its machine map: robots.txt allows everything and declares the sitemap, so Googlebot, Bingbot, GPTBot, ClaudeBot, PerplexityBot, Applebot, and dozens of smaller indexers all read the same two lines.

How It Works

Put robots.txt at the host root with User-agent: *, Allow: /, and one Sitemap line carrying the absolute, canonical URL of the sitemap. Keep sitemap.xml at the URL the robots.txt line declares, listing only canonical pages that return 200 OK and that the owner wants indexed, with honest lastmod dates; split large sites into a sitemap index that lists per-type or per-shard sitemaps. In this build the hub robots.txt was fetched and read: 11 lines, one Sitemap directive, Allow: /, and the welcome note for AI crawlers and bots. A crawler then follows the pointer: it fetches robots.txt, reads the Sitemap line, fetches the sitemap, and adds each listed URL to its crawl queue, keeping full discretion over whether to index any of them.

What It Needs

A robots.txt file at the host root and a sitemap.xml file at the absolute URL the robots.txt Sitemap line declares. No account, no key, no submission. The Sitemap URL must be absolute, never relative.

What It Can Read

Crawlers and AIs read robots.txt first, then the sitemap it points at: the hub's pages, database pages, thesis page, and llms.txt, as listed in the sitemap and its index.

Limits

A sitemap is a discovery hint, not a guarantee: listing a URL guarantees neither crawling nor indexing, and a URL disallowed in robots.txt will not be fetched even if it is listed in the sitemap. Neither file physically blocks access or promises a listing; both are requests that well-behaved crawlers obey. Science Proof

The method rests on crawl-pipeline order: a crawler's first fetch is GET /robots.txt, and only then does it touch a URL, so the robots.txt file is the one place every crawler is guaranteed to look. The Sitemap directive turns that single fetch into a broadcast: one line tells every crawler, including ones the owner has no account with, where the sitemap lives. The sitemap then works at the discovery phase, before any individual URL is queued, which is why it is additive while robots.txt is subtractive: one says what exists, the other says what not to touch.
