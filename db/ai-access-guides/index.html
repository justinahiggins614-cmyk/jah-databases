The Plain-Text Network Guide is the network guide written as plain text, with no formatting, no images, and no scripts, so any reader — person, program, or outside AI — can read it exactly as written. It lists every database, its subject, and its address, one line per database, in a fixed order. The plain-text form is the most portable form the network publishes.

The plain-text guide was designed as the fallback that always works: when a formatted page cannot be read, the plain-text guide still can. The guide is generated from the same manifest as every other guide, so it never disagrees with them. This record does not state a creation date.

A plain-text guide works by writing each database as one line — name, subject, and address — in the manifest's order, with no markup to interpret and no style to load. A reader that can read text can read the guide, and a program can split it into lines and fields without a parser. When a database is added, one line is added, and the guide stays in step with the manifest.

The API cookbook was designed as the recipe book that follows the quickstart: each recipe solves one real task in full, with nothing left out. The recipes are independent, so a developer can read one without reading the others. This record does not state a creation date.

An API cookbook works by giving each recipe its goal, its calls in order, and the expected answer for each call, so the developer can run the recipe and compare the answers. The Developer Onboarding Checklist is the checklist a new developer runs when joining the network: read the overview, read the instructions file, run the quickstart, fetch a database, fetch a file, cite a record, and run the integration tests, each item checked off only when its result matches. The checklist is short enough to finish in one session, and each item names the guide that explains it. It is a guide to the JAH side only.

The onboarding checklist was designed so that a new developer can prove they can use the network, step by step, instead of reading without doing. Each item is a single task with a checkable result. This record does not state a creation date.

An onboarding checklist works by turning the guides into yes-or-no items — did the quickstart call return the expected record, did the citation resolve, did the integration tests pass — and by running them in order, from first reading to first passing test. An item that fails is held for fixing before the next item is attempted. The checklist itself is versioned, so a change to the guides produces a new checklist version.
