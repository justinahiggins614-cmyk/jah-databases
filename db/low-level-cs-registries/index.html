IEEE 754: the floating-point standard Rank 1 · simple

Evidence: established IEEE 754 is an established published standard from 1985, and the bit patterns are verified by direct encoding.

IEEE 754 is the standard for floating-point arithmetic, defining how real numbers are stored as bits and how operations on them behave.

IEEE 754, first published in 1985 and revised in 2008 and 2019, defines how floating-point numbers are stored and how arithmetic on them works, so that the same program gives the same result on every machine. The standard defines the binary32 and binary64 formats, the special values zero, infinity, and NaN, the four rounding modes, and the rules for exceptions such as overflow and division by zero. Without it, every computer would round differently and numerical code could not be trusted across machines. The record gives the standard's scope, its formats, its special values, and its rounding rules, so a reader can check any floating-point value against the standard rather than guessing. It also states the most famous consequence: 0.1 plus 0.2 is 0.30000000000000004 in binary64, because neither 0.1 nor 0.2 is exactly representable in binary.

Decode the binary32 value 0x3FC00000. The sign bit is 0, the exponent field is 127, which minus the bias 127 gives exponent 0, and the mantissa field is 0x400000, which is 1.5 in binary fraction terms: 1 plus one half. The value is 1.5. Encode 0.1 as binary64 instead: the bits are 0x3FB999999999999A, and the value is not exactly 0.1 but the nearest binary64 number to it, which is why 0.1 plus 0.2 gives 0.30000000000000004.

History

The standard was driven by William Kahan at Berkeley in the late 1970s and published by the IEEE in 1985 as IEEE 754-1985. It replaced a chaos of incompatible formats with one rule, and it was adopted by every major processor and language. The 2008 revision added the decimal formats and the 2019 revision clarified them; the binary formats at the heart of this pair have been stable since 1985.

Binary32: sign, exponent, and mantissa Rank 2 · simple

Evidence: established Binary32 is defined by IEEE 754, and the bit patterns are verified by direct encoding.

Binary32 stores a float in 32 bits: 1 sign bit, 8 exponent bits with bias 127, and 23 mantissa bits with an implicit leading 1.

Binary32, the single-precision float, stores a number as three fields: a sign bit, 0 for positive and 1 for negative; an 8-bit exponent field holding the true exponent plus the bias 127; and a 23-bit mantissa holding the fraction after an implicit leading 1. The value is (-1)^sign times 1.mantissa times 2^(exponent - 127), for normal numbers. The record decodes 1.5 as 0x3FC00000: sign 0, exponent field 127, so the true exponent is 0, mantissa 0x400000, so the fraction is 1.5. It also decodes 0.1 as 0x3DCCCCCD, the nearest binary32 number to one tenth, and explains the edge cases: exponent field 0 means zero or a subnormal, and exponent field 255 means infinity or NaN. The record gives the field layout, the formula, and the worked decodings, so any binary32 word can be read by hand.

Decode 0x3DCCCCCD, the binary32 encoding of 0.1. The sign bit is 0. The exponent field is 0x7B, which is 123, so the true exponent is 123 minus 127, which is -4. The mantissa field is 0x4CCCCD, so the fraction is 1 plus 0x4CCCCD over 2^23, about 1.6000000238. The value is 1.6000000238 times 2^-4, which is about 0.10000000149, the nearest binary32 number to 0.1, and the reason 0.1 is not exact in single precision either.

History

Binary32 comes from IEEE 754-1985, where it was defined alongside binary64. The bias-127 exponent and the implicit leading 1 were Kahan's design choices, keeping the format compact and the ordering of floats the same as the ordering of their bit patterns for positive numbers. The format is the float of C, Java, and most graphics hardware.

Special values: zero, infinity, and NaN Rank 4 · simple

Evidence: established The special values are defined by IEEE 754, and the bit patterns are verified by direct encoding.

IEEE 754 defines zero, infinity, and NaN as special bit patterns, with signed zero, infinities from overflow and division by zero, and NaN for invalid operations.

IEEE 754 reserves special bit patterns for values that are not ordinary numbers. Zero has exponent field zero and mantissa zero, and it is signed: +0.0 is 0x00000000 in binary32 and -0.0 is 0x80000000, and the two compare equal but behave differently in division, since 1.0 divided by +0.0 is +infinity and 1.0 divided by -0.0 is -infinity. Infinity has exponent field all ones and mantissa zero: +infinity is 0x7F800000 and -infinity is 0xFF800000 in binary32. NaN, not a number, has exponent field all ones and mantissa nonzero: the quiet NaN is 0x7FC00000, and it arises from invalid operations such as 0.0 divided by 0.0 or the square root of -1.0. NaN has the famous property that it is not equal to itself, so NaN == NaN is false, which is the standard test for it. The record gives the patterns, the operations that produce each, and the comparison rules.

Divide 1.0 by +0.0 in binary64: the result is +infinity, because the exponent overflows. Divide 1.0 by -0.0: the result is -infinity, because the sign follows the divisor. Divide 0.0 by 0.0: the result is NaN, because the operation is invalid. Compare NaN with itself: the result is false, which is how programs test for NaN. Add infinity to 1.0: the result is infinity, because infinity absorbs finite values.

History

The special values were part of IEEE 754 from 1985, designed so that numerical code could continue past an overflow or an invalid operation instead of crashing, with the exception flags recording what happened. Signed zero, infinities, and NaN were Kahan's design, and they are now universal in floating-point hardware and languages.

The evaluation loop fetches each bytecode instruction, dispatches on its opcode, and updates the value stack, one instruction at a time.

The evaluation loop is the heart of CPython: a C loop in Python/ceval.c that fetches the next bytecode instruction, reads its opcode and argument, dispatches to the handler for that opcode, and repeats until the function returns or raises. The value stack holds the intermediate values: LOAD_CONST pushes a constant, BINARY_OP pops two values and pushes the result, STORE_FAST pops a value into a local variable, and RETURN_VALUE pops the return value and ends the frame. The record traces a small function through the loop, shows the stack after each instruction, and explains the dispatch: in CPython 3.11 and 3.12 the loop uses a computed-goto dispatch for speed, and in 3.11 it gained adaptive specialization, where hot instructions rewrite themselves into faster specialized forms. The record gives the loop, the stack discipline, and the specialization note, so the interpreter's execution is visible step by step.

It fetches BINARY_OP with add, pops 2 and 1, adds them, and pushes 3, so the stack reads [3]. It fetches RETURN_VALUE, pops 3, and ends the frame, returning 3. Reference counting and the garbage collector Rank 11 · compounded

Evidence: established Reference counting and the cyclic collector are established public documentation in the CPython C API reference and gc module.

CPython frees memory by reference counting, with a cyclic garbage collector in three generations for the cycles counting cannot reach.

CPython frees memory mainly by reference counting: every PyObject carries ob_refcnt, and when the count falls to zero, the object is freed immediately. Assignment increments the count, deletion decrements it, and passing an object to a function increments it for the call. Reference counting cannot free cycles, such as a list that contains itself, because each member holds a reference to the other and the counts never reach zero. The cyclic garbage collector handles those: it tracks container objects in three generations, 0, 1, and 2, and periodically scans for unreachable cycles, promoting survivors to older generations. The record gives the counting rule, the cycle problem with the self-referential list, the three generations, and the module gc that controls the collector, including gc.collect to force a run and gc.disable to stop it.

Create a list x = [] and append it to itself: x.append(x). The list's ob_refcnt is at least 2, one from the name x and one from the list containing itself. Delete the name with del x: the count falls by one but stays above zero, because the list still references itself, so reference counting cannot free it. The cyclic collector finds the unreachable cycle and frees the list. A plain list with no cycle, by contrast, is freed the moment its last reference is dropped, with no collector run needed.

The Global Interpreter Lock Rank 12 · compounded

Evidence: established The GIL is established public documentation in the Python glossary and threading documentation.

The Global Interpreter Lock, or GIL, is a mutex that lets only one thread run Python bytecode at a time in CPython.

The Global Interpreter Lock, the GIL, is a mutex in CPython that protects the interpreter's shared state: only one thread can hold it, so only one thread runs Python bytecode at a time, even on a machine with many cores. Threads take turns holding the GIL, switching every few milliseconds or when they block on input and output, so threaded Python programs interleave rather than run in parallel. The record gives the rule, the consequence, and the workarounds: threads help when the work waits on input and output, because a waiting thread releases the GIL, but threads do not speed up CPU-bound Python code, because the GIL serializes it. For CPU-bound parallelism the record names the alternatives: multiprocessing, which runs separate interpreters, and, from Python 3.13, the experimental free-threaded build that can disable the GIL. The record is about the GIL as documented for CPython 3.11 and 3.12, where the GIL is always on.

Two threads each count to ten million in Python. With the GIL, they interleave: one runs for a few milliseconds, then the other, and the total time is about the same as running both counts in one thread, because only one runs bytecode at a time. Two threads each downloading a file, by contrast, finish in about half the time of one after the other, because each thread releases the GIL while it waits for the network. The difference is the lesson: the GIL serializes CPU work and frees waiting work.

History

The GIL dates to Python's early threading support in the 1990s, when it was the simplest way to keep the interpreter's reference counting safe. It has been debated ever since, and the free-threaded build in Python 3.13, released in 2024, is the first official path to running without it. The GIL's behavior is documented in the CPython threading documentation and in the Python glossary.

Start two threads: only one can hold the GIL and run bytecode at a time.; Let the threads switch: the GIL passes between them every few milliseconds or on blocking calls.; Use threads for input and output work, where a waiting thread releases the GIL.; Do not use threads for CPU-bound Python work: the GIL serializes it.; For CPU parallelism, use multiprocessing or, from 3.13, the free-threaded build..

Packfiles and delta compression Rank 23 · complex

Evidence: established Packfiles and delta compression are established public documentation in the Git book and the git manual pages.

Git packs objects into packfiles, compressing them with zlib and storing similar objects as deltas against a base, so repositories stay small.

Loose objects, one compressed file per object, are simple but wasteful, so Git packs them into packfiles: a pack holds many objects in one file, each compressed with zlib, and similar objects are stored as deltas, a base object plus the differences, so a file that changes slightly across commits is stored once as a full object and then as small deltas. A pack index, the .idx file, maps each hash to its offset in the pack, so any object can be found by hash without scanning the whole file. The record gives the pack format, the delta rule, and the worked example: ten versions of a file are stored as one base and nine deltas, so the pack is far smaller than ten full copies, and git gc repacks loose objects into packs and prunes the loose ones. It also notes the delta search: Git picks the base by similarity, preferring objects of the same type and similar size, and limits the delta chain depth so a read never follows too many deltas.

A file with ten versions, each 1000 bytes, where each version changes one line. As loose objects the ten versions take about 10000 bytes. As a pack, the first version is stored whole, about 1000 bytes, and the other nine are stored as deltas, each about 50 bytes, so the pack takes about 1450 bytes, roughly a seventh of the loose size. Reading version ten follows its delta chain back to the base and applies the nine deltas in order.
