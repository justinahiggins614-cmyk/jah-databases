Software Testing Center: Application Programming Interface (API)

JAH-STC-000005 — software testing center record

The Application Programming Interface (API) is the machine-readable contract of the Software Testing Center: the set of calls another program may make, what each call needs, and what it returns. Every call is named, its inputs are listed with their types, and its outputs are listed with their shapes, so that a program written against this contract works the first time. A malformed call is answered with a clear error that names the problem, never with silence and never with a crash. In this public edition the program offers 8 capabilities (executing a test suite and recording every result (1); comparing actual output with expected output byte for byte (2); running tests in isolation so one failure cannot hide another (3); a permanent test record with date and evidence (4); re-running any suite on demand (5); plain-text test reports readable without JavaScript (6); an API other programs use to run tests (7); a failing test that names the test, the input, and the difference (8)), 6 interfaces (Suite picker — choose the test suite to run; Run button — execute the suite and watch each test report; Result list — every test with pass or fail and its evidence; Failure view — the failing test, its input, expected output, and actual output; Testing API — machine-readable test running for other programs; Plain-text mode — the test report as readable plain text), and 8 data fields (suite — the test suite that ran; tests — the tests in the suite; passed — how many passed; failed — how many failed, with names; evidence — what each test proved; run_date — the date the suite ran; failures — each failure with input, expected, and actual output; verdict — pass only when failures are 0). This record is number 5 of 24 in the public edition of the Software Testing Center database pair, and it specifies the application programming interface (api) topic in full — what it is, how it works, what it accepts, what it returns, and how it is tested — so that a builder can build it and a tester can verify it without guessing.
